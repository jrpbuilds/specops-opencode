# Compatibility review

Use this skill when a change could affect an existing caller, persisted format, public API, configuration contract, or upgrade path. The consuming review lens decides which question matters; this skill supplies compatibility expertise for answering it. Start with the repository's actual consumers and version policy, not with a generic definition of backward compatibility. For a small bounded change, inspect the changed public or supported contract, one existing consumer, and one old/new compatibility direction; expand only when formats, mixed versions, or deprecation create another risk.

## Inventory the changed surface

Identify every boundary whose meaning, shape, timing, or accepted input may have changed:

- exported functions, classes, types, and module entry points;
- API paths, request and response fields, status or error meanings;
- command-line flags, environment variables, configuration keys, and defaults;
- serialized files, database records, events, messages, and cache entries;
- documented examples, generated clients, fixtures, migrations, and operational scripts.

Record the stability level and support claim for each surface and whether consumer updates can be coordinated. Read callers and consumers directly. A type declaration or schema does not prove that older callers tolerate a new field, changed omission semantics, reordered output, altered error, or different timing. An undocumented surface may still be a de facto contract when external or independently deployed consumers rely on it; an incidental private helper should not be promoted to a public guarantee without evidence.

## Classify the contract change

For each consumer class, classify every applicable dimension:

- **Source compatibility:** existing code, generated clients, imports, and compile-time contracts still build and call the surface.
- **Wire or data compatibility:** old and new readers, writers, providers, and consumers can exchange the representation safely.
- **Semantic compatibility:** defaults, presence, ordering, errors, timing, side effects, and interpretation preserve the supported meaning.

Within each dimension, state whether the change is additive, behavior-changing, or breaking. Support the classification with an actual caller, reader, writer, fixture, or documented contract. Do not call a change compatible only because the type checker accepts it.

## Challenge serialization and configuration

Trace old and new readers and writers through omitted fields, explicit nulls, defaults, unknown fields, enum values, ordering, precision, escaping, and error handling. For persisted or exchanged data, determine whether:

- older readers can ignore new data safely;
- newer readers can interpret existing data without guessing;
- partial writes, interrupted migrations, and malformed records have a deliberate outcome;
- configuration generated by an older version still loads with the intended meaning;
- a value that used to be absent is now indistinguishable from an explicit default.

Use repository fixtures and real parsers where the format itself is the contract.

## Challenge upgrade paths and callers

Consider mixed-version windows, rolling deployment, existing persisted state, cached data, generated clients, and a downgrade or rollback path when the repository supports one. Check all alternate callers, not just the primary route or the most obvious test.

Build the directional matrix that the deployment can reach: old consumer with new provider, new consumer with old provider, old reader with new data, and new reader with old data. Include only possible combinations, but do not infer the reverse direction from evidence in one direction.

An approved breaking change may still require a migration, compatibility window, clear failure, or caller update. An unapproved breaking change is not made safe by adding a note after the implementation.

When the project claims semantic versioning or another public release policy, verify that the release increment, deprecation window, documentation, and migration path agree with the classified change. Deprecation should give supported consumers a usable transition before removal; an approved break is still released incorrectly when its version contract is wrong.

## Verify with consumer evidence

Use call-site inspection, compatibility fixtures, old/new serialization tests, migration tests, and integration checks at the boundary that owns the risk. Assert the observable contract: accepted inputs, output shape and meaning, omitted/default behavior, ordering, error mapping, side effects, and upgrade behavior. Separate a directly exercised consumer from one that was only inferred to be compatible.

## Keep the review bounded

Approved OpenSpec artifacts, current repository behavior, and project conventions decide which compatibility guarantees apply. Report only material, evidence-supported compatibility concerns reachable through the assigned change; do not demand support for consumers or versions the project does not claim to support.
